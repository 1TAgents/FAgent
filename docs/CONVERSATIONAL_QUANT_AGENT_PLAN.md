# FAgent 对话式量化投资经理路线计划

> 创建日期：2026-04-28  
> 目标：把 FAgent 从“聊天入口 + 行情/回测工具雏形”演进为“对话驱动的量化投研、模拟交易、复盘和策略进化工作台”。  
> 说明：本文是后续实施计划，不代表所有功能已经完成。当前实现状态应以根目录 `README.md`、代码和测试为准。

## 1. 最终目标

FAgent 的最终产品目标是：用户通过自然语言对话，就能完成一个专业投资经理日常需要处理的主要量化投资环节。

核心闭环：

```text
对话输入
  -> 任务识别与拆解
  -> 行情、基本面、行业、资金、历史数据查询
  -> 策略假设生成
  -> 策略参数配置
  -> 回测与指标分析
  -> 参数优化与样本外验证
  -> 风险检查
  -> 模拟下单与组合管理
  -> 盘后复盘
  -> 经验沉淀到 Memory
  -> 下一轮策略升级
```

用户体验上，FAgent 不应该只是回答“怎么看某只股票”，而应该能把模糊需求转成可执行任务。例如：

- “帮我看看贵州茅台最近怎么样”  
  系统应自动查询行情、K 线、行业、资金流，给出客观数据摘要和风险提示。
- “用双均线策略回测一下茅台过去一年”  
  系统应执行确定性回测，返回收益、回撤、夏普、交易次数、资金曲线和回测 ID。
- “帮我优化一下参数，不要过拟合”  
  系统应做参数搜索、样本内/样本外切分、稳健性评估，并保存优化 run。
- “如果我现在按这个策略模拟买入 10 万，后面每天帮我复盘”  
  系统应创建模拟账户订单、持仓、每日复盘任务和长期记忆。

## 2. 当前基础判断

### 2.1 已经具备的基础

FAgent 当前已经有比较好的工程起点：

1. 三层服务架构已经成型：`frontend`、`backend`、`agents`。
2. Backend 已经有会话、消息、认证、SSE 流式响应和模型代理。
3. Agents 已经有 Router，能把请求分到 `market`、`strategy`、`backtest`、`trade`、`chat`。
4. MarketSubAgent 已接入 MCP 行情工具，支持行情、K 线、搜索、趋势分析等方向。
5. MCP Server 已经注册较多金融工具，包括行情、K 线、指数、行业、资金流、龙虎榜、融资融券、回测、网格搜索等。
6. BacktestSubAgent 已经接入标准回测主链路，并能返回 `report_id` 和 artifact 目录。
7. BacktestRunStore 已经具备审计意识，会保存请求、报告、策略源码、资金曲线和 manifest。
8. Memory 模块已有独立的会话、消息、摘要、工具响应等基础模型和 SQLite 存储。

### 2.2 主要短板

当前还没有形成完整投资经理闭环，主要短板如下：

1. StrategySubAgent 仍是占位，无法真正完成策略列表、策略解释、策略生成、策略参数模板、策略版本管理。
2. TradeSubAgent 仍是占位，没有模拟账户、订单、成交、持仓、风控，更没有真实交易接口。
3. 参数优化工具虽然在 MCP 中已有注册，但聊天主链路还没有真正接通。
4. 本地数据中台还不稳定，`stock_data.db` 的股票和 K 线表可能为空，回测依赖动态数据源，复现性不足。
5. 回测引擎还需要优先校正：持仓状态、手续费、滑点、A 股交易规则、年化收益、样本外验证等。
6. Memory 没有进入 Router 和 SubAgent 的上下文构造，历史策略结论和用户偏好不能自动复用。
7. 工具调用结果还没有统一沉淀为可检索、可复盘、可审计的事件流。

## 3. 产品定位

推荐定位：

```text
对话式量化投研与模拟投资经理工作台
```

短期不要直接做成实盘交易平台，也不要一开始复制 quantmind 的完整微服务复杂度。更合理的顺序是：

1. 先做可靠的对话式研究员。
2. 再做可信的回测员和策略优化员。
3. 再做模拟基金经理。
4. 最后才接入真实交易网关。

这条路径的好处：

- 风险可控。
- 更容易验证用户体验。
- 更容易调试量化结果。
- 可以逐步沉淀策略、数据、记忆和审计体系。

## 4. 目标架构

### 4.1 分层架构

建议逐步形成以下分层：

```text
Frontend
  - 对话界面
  - 任务状态流
  - 行情和回测可视化
  - 策略与组合面板
  - 复盘报告查看

Backend
  - 用户、会话、消息
  - 任务与 artifact 管理
  - 模拟账户、订单、持仓
  - API 鉴权和权限隔离
  - 报告、复盘、审计查询

Agents
  - MainRouter
  - MarketSubAgent
  - StrategySubAgent
  - BacktestSubAgent
  - PortfolioSubAgent
  - ReviewSubAgent
  - TradeSubAgent
  - Memory/Context Builder

MCP Tools
  - market data tools
  - strategy tools
  - backtest tools
  - optimize tools
  - portfolio tools
  - paper trading tools
  - memory tools

Data Layer
  - market data store
  - feature store
  - backtest run store
  - strategy registry
  - memory database
  - paper trading ledger
```

### 4.2 Agent 职责边界

#### MainRouter

职责：

- 识别用户意图。
- 拆解复杂任务。
- 选择 SubAgent。
- 注入必要上下文。
- 控制工具执行顺序。
- 输出任务状态事件。

后续要增强：

- 不只返回单个 route，而是支持 task plan。
- 支持多步骤任务，例如“先查行情，再回测，再优化，再给建议”。
- 支持任务状态：`planned`、`running`、`tool_calling`、`completed`、`failed`、`need_confirmation`。

#### MarketSubAgent

职责：

- 查询行情、K 线、指数、行业、资金流、财务、龙虎榜等数据。
- 对数据质量和数据来源做说明。
- 给 StrategySubAgent 和 BacktestSubAgent 提供标的上下文。

重点不是输出主观预测，而是输出可信数据摘要。

#### StrategySubAgent

职责：

- 列出可用策略。
- 解释策略逻辑。
- 将自然语言转成结构化策略 spec。
- 管理策略参数模板。
- 生成策略候选。
- 保存策略版本。

策略 spec 示例：

```json
{
  "strategy_id": "dual_ma",
  "name": "双均线趋势策略",
  "market": "A股",
  "universe": ["600519"],
  "frequency": "1d",
  "params": {
    "short_period": 5,
    "long_period": 20
  },
  "risk": {
    "max_position_pct": 0.95,
    "stop_loss_pct": 0.08
  }
}
```

#### BacktestSubAgent

职责：

- 执行标准回测。
- 执行参数优化。
- 执行样本外验证。
- 对比多个 run。
- 解释回测指标。
- 识别过拟合风险。

后续应避免只返回“收益率很高”。必须同时返回：

- 数据区间。
- 数据源版本。
- 策略版本。
- 交易成本假设。
- 年化收益。
- 最大回撤。
- 夏普比率。
- Calmar。
- 胜率。
- 盈亏比。
- 换手率。
- 交易次数。
- 样本外表现。
- 可复现 artifact。

#### PortfolioSubAgent

建议新增。

职责：

- 管理模拟组合。
- 计算仓位、现金、持仓、市值、收益。
- 处理调仓建议。
- 支持多策略、多标的组合。
- 做组合风险归因。

#### TradeSubAgent

职责分两阶段：

第一阶段只做模拟交易：

- 下单预检。
- 创建模拟订单。
- 撮合成交。
- 更新持仓。
- 查询订单和持仓。
- 撤单。

第二阶段再接真实交易：

- QMT。
- miniQMT。
- easytrader。
- vnpy gateway。
- TqSdk。

真实交易必须加：

- 二次确认。
- 风控检查。
- 限额。
- kill switch。
- 审计日志。
- 权限隔离。
- 凭据加密。

#### ReviewSubAgent

建议新增。

职责：

- 对每日行情、持仓、策略表现做复盘。
- 判断策略是否偏离预期。
- 提取失败原因和改进方向。
- 写入 Memory。
- 生成日报、周报、策略复盘报告。

复盘输出示例：

```text
今日复盘：
1. 组合收益：+0.42%，跑赢沪深 300 0.18 个百分点。
2. 主要贡献：600519 贡献 +0.31%。
3. 策略行为：双均线策略维持持仓，无新增交易信号。
4. 风险变化：回撤仍在允许范围内，波动率略升。
5. 后续动作：继续观察，若短均线下穿长均线则触发减仓。
```

## 5. 开源项目参考方案

### 5.1 量化侧

#### rqalpha

最应该优先参考。

参考点：

- 账户、订单、成交、持仓模型。
- 撮合模块。
- 交易成本。
- 风控模块。
- 回测结果分析。
- mod 插件机制。

FAgent 当前最需要补的是回测真实性，所以 rqalpha 的价值最高。

#### qlib

适合中后期接入。

参考点：

- 数据、特征、模型、实验、回测分层。
- Alpha158/Alpha360 因子体系。
- YAML 工作流。
- 训练、预测、评估闭环。

不建议当前就重度接入 qlib。先把基础投研和回测闭环做好，再接 AI 多因子和模型训练。

#### vnpy

适合交易执行层参考。

参考点：

- 事件引擎。
- MainEngine。
- Gateway 抽象。
- 订单、成交、持仓、账户标准对象。
- 交易接口插件化。

后续真实交易接入时，可以参考 vnpy 的 gateway 思路，不一定直接引入整个桌面生态。

#### TqSdk

适合期货和目标仓位体验参考。

参考点：

- 策略、模拟、实盘 API 尽量同构。
- 目标仓位任务。
- wait_update 循环。
- TWAP 和风控工具。

如果 FAgent 后续重点做国内期货，可以优先接 TqSdk。

#### easytrader / QMT

适合 A 股执行桥接参考。

参考点：

- miniQMT。
- 券商客户端桥接。
- 远程交易代理。

风险：

- UI 自动化脆弱。
- 凭据和远程调用风险高。
- 必须先有风控和审计。

#### quantmind

适合作为完整产品闭环参考。

参考点：

- 训练、推理、回测、实盘、前端控制台的产品组织。
- QMT Agent。
- 启动前预检。
- 账户快照保护。
- 手动执行任务。

不建议照搬完整微服务复杂度。

## 6. Message 与 Memory 设计

### 6.1 Message 目标

FAgent 的 message 不能只是 `role/content`。它应该同时服务：

1. LLM 上下文。
2. UI 展示。
3. 工具调用回放。
4. 投研审计。
5. Memory 提取。
6. 任务恢复。
7. 复盘报告生成。

建议新增结构化事件表或扩展现有消息 metadata。

事件类型建议：

| 类型 | 用途 |
| --- | --- |
| `user_intent` | 用户意图解析 |
| `task_plan` | 多步骤任务计划 |
| `route_decision` | 路由结果 |
| `tool_call` | 工具调用 |
| `tool_result` | 工具结果摘要 |
| `market_snapshot` | 行情快照 |
| `strategy_spec` | 策略配置 |
| `backtest_run` | 回测记录 |
| `optimization_run` | 参数优化记录 |
| `risk_check` | 风控检查 |
| `paper_order` | 模拟订单 |
| `portfolio_snapshot` | 组合快照 |
| `review_summary` | 复盘摘要 |
| `memory_extraction` | 记忆提取 |

### 6.2 Memory 分层

建议 FAgent 的 Memory 分为五层。

#### L1 最近上下文

来源：

- 当前会话最近消息。
- 当前任务状态。
- 当前工具结果摘要。

用途：

- 让当前任务顺利完成。

#### L2 会话摘要

来源：

- 当前会话压缩摘要。
- 已完成任务摘要。

用途：

- 防止长会话丢失目标。
- 后续继续同一任务。

#### L3 用户偏好

来源：

- 用户主动表达。
- 系统从对话中提取并确认。

示例：

- 偏好 A 股。
- 不接受高回撤。
- 更关注趋势策略。
- 初始资金 10 万。
- 不做真实交易，只做模拟。

#### L4 投研记忆

来源：

- 历史策略研究。
- 回测结论。
- 参数优化结果。
- 复盘总结。

示例：

- “600519 上双均线 5/20 在 2025-04-27 到 2026-04-27 表现为 +8.14%，最大回撤 -1.08%。”
- “用户上次认为 RSI 策略交易过频，希望降低换手。”

#### L5 Artifact 索引

来源：

- 回测 artifact。
- 策略源码。
- 资金曲线。
- 交易明细。
- 复盘报告。

用途：

- 按 `report_id` 精确追溯。
- 多 run 对比。
- 复现实验。

### 6.3 Memory 接入点

建议按顺序接入：

1. Backend 每次保存消息时，同步写入 Memory 原始消息或建立映射。
2. Agents 每次工具调用后，保存工具响应摘要和 artifact 链接。
3. BacktestSubAgent 每次完成回测后，写入投研记忆。
4. ReviewSubAgent 每次复盘后，写入长期记忆。
5. Router 构造上下文时检索相关记忆。

## 7. 数据与回测优先级

### 7.1 数据中台目标

短期目标不是做大而全数据平台，而是保证回测可复现。

最低要求：

1. 所有回测使用的数据必须有数据源记录。
2. 每次动态拉取的数据必须能落库。
3. 回测报告必须记录数据快照版本。
4. 缺失数据、停牌、复权方式必须可见。
5. 同一个请求在同一数据快照上能复现同一结果。

建议数据源优先级：

```text
本地数据快照
  -> RQData
  -> AKShare
  -> 失败说明
```

### 7.2 回测正确性必须先修

在做复杂策略之前，先修标准回测。否则后续所有优化和复盘都会建立在不可靠结果上。

必须补齐：

1. 持仓状态 forward-fill，不能只在信号当天计算收益。
2. A 股买卖单位，默认 100 股整数倍。
3. 手续费、印花税、过户费统一接入。
4. 滑点模型。
5. 停牌处理。
6. 涨跌停无法成交处理。
7. 成交价模型，例如次日开盘、当日收盘、VWAP。
8. 年化收益按交易日数计算，不能简单等于总收益。
9. 交易明细必须保存。
10. 策略源码 hash 和参数必须入 artifact。

### 7.3 回测验收标准

完成后，至少要有以下测试：

1. 单调上涨价格序列下，买入持有策略收益正确。
2. 无信号时资金曲线保持不变。
3. 买入后无卖出时，资金曲线随持仓价格变化。
4. 手续费降低最终收益。
5. 100 股规则导致现金有剩余。
6. 同一数据快照和参数重复回测，结果完全一致。
7. 回测报告能通过 `report_id` 完整加载。

## 8. 阶段计划

## Phase 0：整理基线与测试护栏

目标：

建立当前系统真实状态，避免后续开发在不稳定基础上继续叠加。

任务：

1. 更新 README 中“当前状态”和“启动服务”说明。
2. 标注哪些工具已注册、哪些已接入聊天主链、哪些仍是占位。
3. 梳理端口：Backend 8000、Agents 8001、MCP 8002、Data Sync 8003。
4. 增加一键 smoke test：
   - 创建会话。
   - 普通聊天。
   - 行情查询。
   - K 线查询。
   - 标准回测。
   - report 加载。
5. 固化最小测试数据集，避免每次测试都依赖外部网络。

验收：

- 新人能按文档启动完整链路。
- smoke test 能稳定跑通。
- 当前占位能力在文档中清楚标注。

建议周期：

- 2 到 3 天。

## Phase 1：可信行情与数据快照

目标：

把“查行情”和“拉回测数据”变成可解释、可复现的数据服务。

任务：

1. 修复 `stock_data.db` 为空时的数据初始化流程。
2. 建立 `market_data_snapshot` 概念。
3. 每次回测记录：
   - 数据源。
   - 拉取时间。
   - 复权方式。
   - 交易日数量。
   - 缺失率。
4. MarketSubAgent 输出数据来源和时间戳。
5. MCP 工具返回统一格式：
   - `success`
   - `data`
   - `source`
   - `timestamp`
   - `quality`
   - `warnings`
6. 增加数据质量检查：
   - 空数据。
   - 重复日期。
   - OHLC 异常。
   - 成交量缺失。

验收：

- 查询 600519 行情能返回数据源和时间戳。
- 回测 600519 过去一年能保存数据快照信息。
- 数据缺失时，Agent 明确告诉用户缺失原因，而不是编造分析。

建议参考：

- QUANTAXIS 的数据中台思路。
- qteasy 的本地数据管理体验。

## 11. 安全与风控原则

量化和交易系统必须把安全放在早期设计里。

最低原则：

1. 默认只允许模拟交易。
2. 真实交易必须显式启用。
3. 真实交易必须二次确认。
4. API Key、券商凭据不能进入普通日志。
5. 工具调用必须有审计。
6. 交易接口必须有 kill switch。
7. 每个账户有最大单笔交易额。
8. 每个账户有最大仓位限制。
9. 每个策略有最大回撤阈值。
10. Agent 不能绕过风控直接下单。

## 12. 优先级总表

| 优先级 | 事项 | 原因 |
| --- | --- | --- |
| P0 | 回测正确性 | 后续优化、复盘、模拟交易都依赖可信回测 |
| P0 | 数据快照与复现 | 否则历史报告不可验证 |
| P0 | StrategySubAgent 实装 | 这是从“查数据”到“做策略”的关键 |
| P1 | 参数优化接入聊天 | 用户目标中明确包含策略优化升级 |
| P1 | Run 对比 | 投资经理日常必须比较策略和参数 |
| P1 | Paper Trading | 下单接口可先空着，但模拟交易必须先有 |
| P1 | Memory 接入主链路 | 对话式工作台必须能延续历史上下文 |
| P2 | 复盘日报/周报 | 形成专业投研闭环 |
| P2 | qlib/AI 因子 | 基础闭环稳定后再做 |
| P3 | 真实交易接口 | 风险最高，最后做 |

## 14. 关键验收场景

### 场景 1：行情研究

用户：

```text
帮我看看贵州茅台最近一周走势，顺便看一下行业情况。
```

系统应：

1. 识别 600519。
2. 查询近一周 K 线。
3. 查询实时或最近行情。
4. 查询所属行业或行业行情。
5. 输出数据来源和时间。
6. 给出客观分析和风险提示。

### 场景 2：策略回测

用户：

```text
用 5/20 双均线回测贵州茅台过去一年，初始资金 10 万。
```

系统应：

1. 生成策略 spec。
2. 加载可复现数据。
3. 执行回测。
4. 返回指标。
5. 保存 artifact。
6. 返回 `report_id`。

### 场景 3：参数优化

用户：

```text
帮我优化一下短均线 3 到 15，长均线 20 到 80，不要过拟合。
```

系统应：

1. 读取上一策略上下文。
2. 生成参数网格。
3. 样本内训练。
4. 样本外验证。
5. 返回最优和稳健参数。
6. 提示过拟合风险。
7. 保存 optimization artifact。

### 场景 4：模拟交易

用户：

```text
用优化后的策略模拟买入 600519，最多 20% 仓位。
```

系统应：

1. 读取优化后策略。
2. 查询当前模拟账户。
3. 做风控预检。
4. 要求用户确认。
5. 确认后创建模拟订单。
6. 更新持仓。
7. 记录交易理由。

### 场景 5：复盘

用户：

```text
复盘一下我这个策略最近的表现，看看要不要调整。
```

系统应：

1. 读取策略和持仓。
2. 查询近期行情。
3. 对比基准。
4. 分析收益来源和回撤来源。
5. 判断策略是否失效。
6. 给出下一步动作。
7. 写入 Memory。

## 15. 不建议做的事

短期不建议：

1. 直接接真实交易。
2. 直接复制 quantmind 的完整微服务架构。
3. 在回测不准前做复杂 AI 模型。
4. 把所有量化开源项目依赖装进同一个 Python 环境。
5. 让 LLM 自由生成 Python 策略并直接执行，除非有沙盒和审计。
6. 只追求“收益很高”的回测报告。
7. 忽略数据源版本和复现。
8. 把 Memory 当成普通聊天历史，而不是投研资产。

## 16. 最终形态

FAgent 最终应具备三种身份：

1. **量化研究员**  
   能查数据、解释行情、构建策略假设。

2. **回测与优化工程师**  
   能执行可信回测、参数优化、样本外验证、run 对比。

3. **模拟投资经理**  
   能管理模拟组合、执行风控、做复盘、沉淀经验。

真实交易只是最后的接口扩展，不是当前最核心的产品价值。

最重要的建设顺序：

```text
可信数据
  -> 可信回测
  -> 策略对话
  -> 参数优化
  -> 模拟组合
  -> 复盘记忆
  -> AI 因子
  -> 真实交易
```

只要这个顺序不乱，FAgent 就能从现在的雏形稳步成长为真正有用的对话式量化投资系统。
